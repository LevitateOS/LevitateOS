# Where each fact lives

- **A distro's declarations:** `distro/variants/<id>/distro.toml`, beside its `kconfig` and `keys/`. `distro_contract::load` reads and validates it; the shape is the `ConformanceContract` type, and `[profile]` holds the facts the distros differ in (also written into the image's os-release as `REC_*`, read through the `distro-profile` crate). Artifact names follow from the distro's `os_id`.
- **Products and scenarios:** one registry, `distro_contract::registry`, the same for every distro. What a scenario expects follows from the scenario, the init system and the identity (`install_tests::expect`).
- **Commands:** `cargo xtask --help`; `xtask/README.md` says what xtask owns.
- **Building products:** `distro/builder` (its README maps the crate).
- **Running scenarios:** `testing/install-tests` (its README maps the scenarios, state and VM launcher).
- **OS recipes:** `distro/builder/os-recipes/` owns acquisition and composition for system images, kernels, tools and live overlays. The builder selects this collection explicitly. The base-package lock is written by `cargo xtask base lock`; the variant declares what to lock. Apps included in a desktop image belong to this OS lifecycle too; `recab` owns system updates and symmetric A/B continuation, coordinating software operations through Recipe.
- **User-managed recipes:** `recipes/` is the separate application catalog, starting with ripgrep. The builder ships it under `/usr/share/recipe/recipes`; root's overrides, active profile and retained state live under `/var/lib/recipe`, shared by A/B slots. Recipe activates a published `package` tree through an atomic profile switch. Updates consume the selected recipe's pin; removal uses the installed receipt without running a recipe.
- **Shared recipe format and engine:** `tools/recipe` owns Rhai API 2, declared needs, dependency resolution and the Ginux lifecycle. Both collections use it unchanged. Recipes own source/package facts and acquire/build/install behaviour; their consumers decide how to use the published outputs. Collection membership is a layout/ownership convention, not a different execution API or permission boundary.
- **Installed system updates and changes:** `tools/recab` owns preparing the inactive system, obtaining and applying updates without losing pending changes, finalization, trial boot, commit and rollback. Installation must populate equivalent personalized A/B systems and both sets of boot artifacts. Continuation must reuse the inactive filesystem and synchronize only differences in either direction. Recipe owns software acquisition/build/install/update/remove inside Ginux; recab owns the destination and system lifecycle. Current destructive `stage`, empty initial B and shared root package activation do not yet implement that contract; see `tools/recab/REQUIREMENTS.md` and the active implementation plan in `tools/recab/IMPLEMENTATION.md`.
- **Output locations:** under `.artifacts`, chosen by the builder's `recipe/outputs.rs` and the install-tests state module, not documented here.

Rules that hold everywhere: recipes own package facts, Rust/TOML owns orchestration; scenarios consume existing artifacts and do not build them; product dependencies form a build graph, not an ordered test ladder; destructive disk operations keep their protections; a cached pass or a successful build is not release evidence for A/B behaviour (update and rollback need their scenario). The admin tool differs by design (sudo or doas), so parity checks exercise the distro's declared tool.
